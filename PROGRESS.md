T11 CLOCK, SIEVE — done 2026-08-29, commit pending amend. Both `stable` in all three languages, both flagged `recommended` per concept §6. 162 TypeScript tests, 60 Python, 8 C tests green under Debug and ASan+UBSan; all 32 hand-authored expectations matched on first generation, and both C implementations passed their vectors on the first run. **The interesting work was finding a case that actually distinguishes CLOCK from SIEVE.** They agree on every obvious small trace — including the example in concept §8.3, where both evict `b` — because a single hit buys one second chance under either policy. They part only once a *survivor's position* matters: with capacity 2, `a b a(hit) c` then evict, then `c(hit) d` then evict, CLOCK evicts `a` (it moved the survivor to the back and the hand returns to the oldest entry) while **SIEVE evicts `d`, the entry inserted a moment earlier**, because it left the survivor in place and its retained hand had already passed it. That is quick demotion in a single step, and it is now the `distinguishing` vector on both entries, each cross-referencing the other. Decisions: (1) CLOCK is implemented as the **queue formulation** (second-chance) rather than a circular buffer with a hand. The two are the same algorithm — re-examining an entry and pushing it back is what advancing a hand past it does, and the queue's front *is* the hand — and the queue form is easier to reproduce identically in three languages. The README documents the equivalence rather than picking a side. (2) SIEVE names its list directions `newer`/`older` instead of the paper's `prev`/`next`, which are ambiguous when the hand travels one way and insertion happens at the other; a dedicated vector pins that the hand is retained across evictions, since restarting it at the oldest entry each time would silently turn SIEVE into CLOCK. (3) Measured C memory: **CLOCK 43.8 bytes/entry, SIEVE 47.8** — I had written 51.8 for SIEVE from an estimate and corrected it against `memory_bytes`. The four-byte gap over CLOCK is exactly the second list link, which SIEVE needs because its hand removes from the middle of the order. Note: one of my tests failed and **the expectation was wrong, not the code** — I asserted SIEVE would beat LRU on a 20-event scan trace, but with the working set hit only once each, SIEVE's first sweep clears every bit and the scan then evicts it exactly as LRU does. Its scan resistance needs the working set re-hit *after* a sweep, which the canonical `scan-heavy` trace provides (and where SIEVE does beat LRU, asserted). I replaced the bad test with one that is true at small scale: with every resident entry visited, both SIEVE and CLOCK reclaim the newcomer while LRU evicts part of the set it is actively serving.

T13 ARC — done 2026-08-29, commit pending amend. Megiddo & Modha's FAST 2003 algorithm from the paper's Figure 4: T1/T2 for entries, B1/B2 for their ghosts, and an integer target `p` that every ghost hit moves. `stable` in all three languages; 182 TypeScript tests, 62 Python, 10 C tests green under Debug and ASan+UBSan. **The conflict guard earned its keep here.** My hand-authored `tiebreak` expectation said the third eviction would come from T2, and generation refused to write the file: `expected "a", got "e"`. Working it out, the implementation was right — every Case IV miss *refills* T1, so T1 never drains on its own and replacement keeps taking from it; reaching T2 requires promoting what is left of T1 first. The corrected vector now says so explicitly, and that is a fact about ARC I would have silently encoded backwards if the generator had simply captured whatever the code did. Decisions: (1) **ARC chooses its victim while handling the miss**, because the REPLACE decision depends on list sizes *before* the new key is inserted, while the interface asks for the victim afterwards. The decision is therefore executed immediately and the key held in `pendingVictim` until `evict()` collects it; `size()` counts it so the helper stays honest, and an unprompted `evict()` is a loud error rather than an improvised eviction. **The distinguishing case is the boundary burst, and it separates all three cleanly.** Five permits a second, five requests at t=999 and five more at t=1000: fixed window admits **ten** — twice its limit in two milliseconds — while the log and the counter admit five. The two that refuse then differ in *how* they recover, which is the more useful comparison and is now pinned by `policies/rate-limiter/window-policies.test.ts`: halfway through the next window the counter has faded three permits back in, while the log holds all five until they expire together at t=1999. Smooth versus stepped, and that is the reason the counter is the usual production choice.

Decisions: (1) **Windows are aligned to the epoch, not to a key's first request.** That is what makes the fixed window and the counter distributable — the window index is a pure function of the clock, so two processes agree without exchanging a message — and it has the visible consequence that a key's first request does not get a full window to itself. Pinned by a boundary vector. (2) **The sliding window is `(now - windowMs, now]`**, half-open at the far end, so an entry exactly `windowMs` old has left. That choice is what makes "at most `limit` in any `windowMs` interval" true as stated rather than off by one, and the log's exactness claim is checked exhaustively rather than at a chosen instant: over 4,000 random arrivals, every window starting at an admitted timestamp is verified to hold no more than `limit`. (3) **The sliding counter's weighting floors, and the floor decides real requests.** With `limit` 5 one millisecond into a new window the exact carried value is 4.995; flooring calls it 4 and admits a request an exact calculation would refuse. That is part of the policy's definition rather than a rounding artefact — it is what will keep the three ports identical — so it has its own vector. (4) The sliding log holds timestamps as doubles rather than `uint32`: a millisecond clock passes 2^32 after 49 days and a limiter should not develop a fault on day 50. Every integer below 2^53 is exact in a double, so this is still integer arithmetic.

**A property test found a real bug, which is why it is now in the suite.** `retryAfter` should be actionable: with a single key and no competing traffic, waiting exactly that long must admit. Checking that across randomised limits and windows, fixed window and sliding log passed on all ~10,500 denials while **sliding counter failed 2,025 of 2,508** — four in five. The cause was that it returned the bare window edge, and at the edge the current count becomes the previous count and, undecayed, refuses again. Because `allow` never lets `current` exceed `limit`, the count sitting there is exactly at the limit and a single millisecond of decay always drops the carried value by one, so the fix is `edge + 1`. A second, smaller bug in the same function came from the same source: the early-out treated a zero "excess" as needing no wait, when zero means the carried count is exactly one too high and still needs that millisecond. T24 token bucket, leaky bucket — done 2026-08-29. **The finding: these two policies are the same algorithm, and the registry now says so with a proof rather than a claim.** The spec asked for a distinguishing vector on "burst handling (token bucket admits burst then refills; leaky smooths)", so I set out to write one — and could not, because at equal parameters no such difference exists. Substituting `tokens = capacity - level` maps each line of one onto the other: a request that fits under the ceiling is a request with a token to spend, draining is refilling, and the level bottoming out at zero is the balance saturating at `burst`. Rather than manufacture a difference, I checked it: `bucket-policies.test.ts` runs 200 randomised configurations for 20,000 decisions and asserts the two agree on every admission, on `retryAfter`, and on the state mapping itself — with a guard that at least 1,000 of those decisions were denials, so two permissive limiters could not agree trivially. `test_ratelimiter.c` re-checks it in C over 600 steps. Zero disagreements anywhere.

What *does* differ is the default, and that is where "leaky smooths" turns out to be true: **`capacity` defaults to 1, not to the domain's reference burst of 100.** A leaky bucket is chosen precisely when you do not want a burst allowance, and at capacity 1 it admits exactly one request every `1000/ratePerSec` ms with no two together — a test pins the admission times as `[0, 10, 20, … 190]` exactly. The token bucket at its default spends 100 at once. So the distinguishing vector became "at its default capacity it smooths to exact spacing", and each policy also carries an `equivalence` case that is a line-for-line mirror of the other's, so the two files can be read side by side. Both READMEs state plainly that the choice is about vocabulary and about which parameter is natural to state, not about behaviour — which is the more useful thing to tell a reader than a manufactured distinction would have been.

Decisions: (1) **Idle time is clamped to a precomputed `fillMs`/`drainMs` before the multiply.** A key untouched for a month would otherwise compute `rate x elapsed` in the billions — harmless in JavaScript, an overflow in C — and the clamp changes nothing observable because the bucket saturates long before. Doing it identically in all three languages is what keeps them bit-compatible; a vector idles a key for a month and asserts the balance is exactly one burst. (2) **A key never seen starts full (token) or empty (leaky)** — the same state under the duality. A bucket that started empty would refuse a first request for a reason no caller could act on. (3) The fractional carry has its own vector in each policy: at three tokens a second the boundary lands on millisecond **334, not 333**, and an implementation that recomputed from scratch or rounded the remainder away would still be at zero there.

**Two guards fired during this item, both correctly.** The C emitter refused to generate until `levelOf` and `tokensOf` were declared introspection-only — the T10 rule that an unknown method is a hard error rather than a silent skip, doing exactly its job on a domain it was written for two items ago. T26 (part 1 of 2) retry infra + constant, exponential, full jitter in TypeScript — 2026-08-29. The domain (interface, episodes, harness, metrics, TRACES.md, 17 tests), three policies with vectors and READMEs, the committed episode prefix, and a cross-policy test. 452 TypeScript tests, catalog valid across 20 policies and 3 domains, every generator idempotent. `status: "experimental"`, `ports: ["ts"]`; **part 2 adds the Python and C ports plus the retry C emitter and trace parity.**

**Two deviations from the plan, both because the specified design would have made the benchmark measure the wrong thing.**

(1) **Two random streams per episode, not one.** The plan pinned a single stream ordered "outage draw, then per-attempt success draw, then policy's `nextDelay` draws". With one stream a policy that draws jitter shifts the position of every later success roll, so two policies would face *different luck* rather than different strategies — and comparing strategies is the entire purpose. The environment stream (outage plus one roll per attempt) and the policy stream are now seeded separately from the episode index. A test drives two policies with identical delays but different draw counts and asserts identical results, which is the property the split buys. Related: the success roll is drawn on **every** attempt rather than only when the outage has passed, so attempt *k* always consumes environment draw *k*; short-circuiting would make the stream position depend on the outage.

(2) **The `Rng` is supplied at construction, not threaded through `nextDelay`.** concept.md §5.1 passes it per call, but every other domain here supplies randomness at construction — the C vtable's `create(params, allocator, rng)` already does — and making retry the exception would put a `pb_rng *` on the C hot path for no benefit. It also lets the generic vector runner drive these policies unchanged, since it already hands the factory an `Rng`. The harness therefore builds the policy **per episode** rather than once, so each gets a fresh independently seeded stream.

**The benchmark could not show why the recommended policy is recommended, so it gained a metric.** Jitter's benefit is dispersing a fleet, and a single-client simulation cannot see it: on the four specified metrics, full jitter looks strictly *worse* than plain exponential (success 0.199 against 0.400) because its expected delay is half. But every episode's first attempt is at t=0, so the thousand episodes are also a thousand clients that failed together — which is exactly the situation jitter is for. `peakRetryShare` measures the largest share of all retries landing in one window, and it separates them sharply: constant 14.4%, exponential 15.1%, **full jitter 2.6%**.

**The window size turned out to be load-bearing, and getting it wrong inverted the result.** At the 100 ms window I first chose, full jitter scored *worse* (18.5%) than exponential (15.1%), because its early draws cluster near zero while exponential's land in distinct buckets. The window has to be small relative to the first delay or it cannot separate "every client at exactly t=100" from "clients spread across [0, 100]". At 10 ms — a tenth of the reference base — the six-fold improvement appears. Both the constant and the reasoning are recorded in the harness, and a test asserts the window stays below the base delay.

Decisions: (1) The three policies **share `backoffCeiling`** rather than restating the doubling, so they cannot drift apart in what they compute before the draw. It multiplies and stops at the cap rather than shifting, so attempt 1,000,000 is safe — a test asks for exactly that. (2) Full jitter's delays are **captured**, because which value a uniform draw returns is a fact about the shared Rng rather than something derivable from the paper; the properties a captured value cannot state — within the ceiling, ceiling reachable, zero reachable, mean about half — are asserted in `index.test.ts` instead. (3) **Giving up consumes no randomness**: the refusal checks precede the draw, so a port that ordered them differently would diverge silently from the first give-up onward, and a test pins it. (4) The reference configuration covers **12.7 seconds** against outages of up to thirty, so most episodes fail for every policy. That is the honest result rather than a broken harness — eight attempts at a 100 ms base is what a default HTTP client does — and both the README and TRACES.md say so plainly.

**The uncomfortable half of the result is reported rather than hidden.** Full jitter succeeds less often than plain exponential on this workload, and `backoff-policies.test.ts` asserts that ordering so it cannot quietly change. A reader who found that number independently would rightly distrust a page that had omitted it.

Two of my own assertions were wrong and the code was right: retries are not evenly distributed across attempt numbers (episodes succeed at different points), and two policies with different delays do not make identical retry counts. Both tests now state exact claims instead of convenient ones.

T29 (part 1 of 2) kv-cache infra in TypeScript — 2026-08-29. The domain opens Phase E: interface, the synthetic attention generator, harness, metrics, TRACES.md and 21 tests, plus a bit-exact committed prefix. 531 TypeScript tests, catalog valid, prefixes idempotent, the other three domains untouched. **Part 2 adds the Python and C generators and the kv-cache trace parity emitter.**

**This is the first domain whose trace is floating-point, which changes what "reproducible" costs.** Everything else in the registry compares integers. Here a single differing ULP in one weight propagates through the normalisation into every other weight of that step, so the parity artefact is **float32 bit patterns** rather than values — two floats that print alike can differ in the last place, and for a generator whose whole job is reproducibility that difference *is* the bug. The committed prefix holds the exact bits of the first ten steps plus an FNV-1a 32 hash over all 4,096, because committing the whole trace would mean eight million floats while the hash says the same thing in one number and the first steps say where a divergence starts.

**The generator is a deliberate caricature, and the caricature is the point.** Four components — sinks at 0.15 on positions 0–3, a recency window at 0.55 over the last 64, 32 scattered heavy hitters at 0.25, and 0.05 of uniform noise — chosen because every policy in this domain exploits one of them, so a workload containing all four separates them. Verified rather than assumed: every step sums to 1.000000, and the heavy component switches on at exactly t=128 with local dropping 0.825 → 0.575 and the middle band jumping 0.023 → 0.273.

Decisions: (1) **Contributions accumulate in a pinned order — sink, local, heavy, noise — in float64, with one division and one `fround` per position at the very end.** Float addition is not associative, so a different order gives a different last bit. No transcendental appears anywhere: the weights are `65 - d` and `1/(rank+1)`, because `pow` and `exp` are not correctly rounded across C standard libraries. (2) **The heavy set is drawn at t=128 and redrawn at every multiple of 512**, and both conditions are pinned. The plan said only "redrawn when t % 512 == 0", which left 128 ≤ t < 512 with no set to draw from; drawing on first use resolves it. Below 128 there is no room between the sinks and the recency window for 32 distinct positions, so the heavy mass folds into local and the total stays at one. (3) **The policy sees attention restricted to what it holds and deliberately not renormalised**, so the weights sum to less than one by exactly the mass already lost. Renormalising would erase the very quantity `retainedAttentionMass` measures, and a policy shown renormalised weights could not tell a healthy cache from a damaged one. (4) `heavyHitterRecall` breaks ties by preferring the lower position — arbitrary, but without a rule the metric would depend on sort stability and stop being reproducible.

**The harness discriminates, checked before anything was built on it.** Two throwaway policies — a plain sliding window and a four-sink StreamingLLM — separate cleanly at every budget: 0.592 against 0.676 retained mass at budget 256, and 0.740 against 0.828 heavy-hitter recall. The gap of 0.084 is exactly the sink mass, which is the arithmetic confirming the harness measures what it claims.

**Both metrics are proxies and the documentation says so at length**, in TRACES.md and again in `metrics.ts`. They measure how much attention a policy kept, not how good the model's output was; the two correlate but the correlation is not a guarantee, and this registry cannot measure the thing itself without shipping a model. The guidance is to use these numbers to narrow a shortlist and confirm against real generations — the papers behind each policy do evaluate that way, which is what these cannot.

One test of mine was wrong rather than the code: I checked the "evicted something it does not hold" guard with position 9,999, which is outside the 4,096-token sequence and so trips the range check first. Both guards are correct; the test now uses a position inside the sequence that the policy cannot yet be holding.

**The anti-circularity check earned its keep.** SnapKV's vectors were rejected on first generation: one hand-authored expectation disagreed with the implementation, and neither turned out to be right. My expectation encoded "a null attention step ages the observation window"; the code advanced the ring without clearing the slot, which would leave a stale weight sitting there for another full cycle — so a window claiming to cover the last sixteen steps would quietly have been summing a value of indeterminate age. The coherent rule, and the one matching H2O and TOVA, is that **a null step is entirely inert**: nothing written, ring not advanced, so the window spans the last `obsWindow` *observed* steps. The fix replaces the guard with modulo indexing over the weight region, which wraps by construction rather than by a condition that has to be got right, and the minimum input length is now five. Worth recording plainly: **the harness is code, and the first thing it found was its own defect.** After the fix, 5,235,287 executions in 121 seconds with no crashes.

**The kv-cache harness is the only one that checks the no-allocation-after-create rule properly.** The cache and rate-limiter bodies compare `memory_bytes` before and after, which a policy could satisfy while freeing and reallocating the same number of bytes on every operation — calling malloc per token, which is exactly the unbounded pause a KV cache cannot afford and precisely what concept.md §12.2 forbids. This harness supplies its own `pb_allocator` and counts the calls, so that policy fails. The plan assumed `pb_allocator` already counted; it does not, and the interface is designed so a caller can supply one that does, which is the better answer than adding counters to the shared allocator.

The harness mirrors the TypeScript harness exactly — position 0 held from the start, `on_decode_step` before the new position joins, `evict` only once the budget is passed — because an invariant checked against a different loop than the one the benchmarks run is checking the wrong thing.

**Three fault injections, one per invariant class, all caught**, per T18's practice of proving a safety net can fail: making `evict` stop one position short reports "evict did not free enough to reach the budget"; making it name a position 1,000 higher than the real one reports "evicted a position out of range"; and adding a single `pb_alloc`/`pb_free` pair to `on_decode_step` — invisible to `memory_bytes`, since the net size is unchanged — reports "allocated after create". That third one is the whole justification for the counting allocator, demonstrated rather than argued.

T41 runner infrastructure — done 2026-08-30. A Web Worker running the registry's real policies over the registry's real traces, a shared control shell with keyboard transport and URL-encoded state, and 24 new tests. 639 TypeScript tests in total, contrast clean, catalog valid.

**Step-back needs no serialisation API, and measuring said so.** The plan proposed a `serialize()`/`restore()` pair on the harnesses with snapshots every 256 steps. Before building that I measured what the naive alternative costs: **replaying all 20,000 steps of a reduced cache trace takes 0.85 ms** [corrected in T42: re-measured on the backwards-seek path it is 2 ms; the conclusion below stands] — 5% of one 60fps frame. So "the state at step N" is simply "a fresh policy, replayed N times", which is not an approximation of the real state but *is* the real state, and it needs nothing added to 30 policies in three languages. A serialisation surface would have been more code, in more places, that could drift from the behaviour it claimed to capture. A property test seeks to a hundred steps in shuffled order and asserts each lands identically to walking there forwards, which is what catches a reset that forgot a field.

**The steppers reimplement the harness loops, and a test is the only thing making that safe.** A runner has to stop between events; `runCacheTrace` and its siblings do not. So `simulation.ts` duplicates each loop — and `simulation.test.ts` runs every stepper to completion and compares against the harness itself, on five combinations across three domains. It found two real defects immediately: the cache stepper produced `hitRate: NaN` because I built the metrics input without `events`, and the rate-limiter stepper omitted `maxBurst100ms`, `keysSeen` and the Jain sums entirely. Both would have shipped a runner quietly disagreeing with the site's own tables, which is worse than having no runner. Notably the **eviction counts matched exactly** in the failing runs — 824 and 843 — so the loops were right and only the metric plumbing was wrong, which is precisely what a comparison against the real harness distinguishes and an eyeball would not.

Two of the five parity cases exist to close a specific hole: **the kv-cache pair uses StreamingLLM and then H2O**, because StreamingLLM ignores the attention vector entirely and would agree even if the runner passed it nonsense. H2O reads every weight.

**A real build failure worth recording.** Vite defaults `worker.format` to IIFE, which cannot code-split — and the worker loads policies by dynamic import, so its bundle must split. Setting `worker.format: "es"` makes the build agree with the code, which already constructs the worker as `{ type: "module" }`. The emitted `sim-worker-*.js` chunk plus per-policy chunks confirm the real implementations are what reaches the browser.

Decisions: (1) **The worker owns every simulation being compared and steps them in lockstep**, which is what makes a side-by-side comparison mean anything — same events, same order, same seed. (2) **State lives in the URL fragment, not the query string**, so it never reaches a server and never appears in a log; the site claims to make no request a reader did not ask for and this keeps that true. The encoding is readable (`#d=cache&p=sieve,lru&t=scan-heavy`) because a link someone can edit by hand is worth more than a compact one they cannot, and the decoder never throws — a typo lands on a working page carrying whatever was legible. (3) **The fragment is replaced, never pushed.** Pushing a history entry per step would make the back button walk backwards through a thousand events instead of leaving the page. (5) **Pressing play at the end restarts** rather than doing nothing under a button that says "pause". T42 cache runner + visualization — done 2026-08-30. Two canvases per policy: the resident set with each entry's real decision bit, and hit rate over time against a dashed Bélády OPT reference. 1.8 KB gzipped against a 20 KB budget, 19 new tests, 658 TypeScript tests in total, contrast clean.

**The runner was replaying traces that did not contain their own subject matter.** T41 replayed a flat 20,000 events of every trace. But `scan-heavy` injects a scan every 20,000 accesses and `shifting-popularity` rotates its hot set every 25,000 — so a 20,000-event prefix of either contains *none* of it. The runner was replaying plain Zipf under a name promising otherwise, directly beside a benchmark table reporting the real trace. I found it by chasing something that looked like a bug and was not: SIEVE and LFU scored *identically* on the reduced trace, to the last hit. That turned out to be true and worth knowing — under stationary Zipf the cold tail is accessed once per key, so LFU chooses among an all-zero-frequency set in insertion order while SIEVE scans its all-unvisited entries in the same order, and they evict the same 4,999 victims in the same sequence. But the committed benchmarks have them at 0.610 and 0.323 on shifting-popularity, and the runner showed them tied on every trace it offered. The prefix, not the policies, was wrong.

So the reduction is now per trace: a scheduled trace gets enough events for its behaviour to happen **twice**, since the second occurrence is where policies visibly come apart and the first alone can read as a blip. `scan-heavy` runs 50,000 events and `shifting-popularity` 62,500. SIEVE and LFU now finish 0.13 apart where they used to tie, and scan resistance is visible where it previously was not. `SCAN_INTERVAL` and `SHIFT_INTERVAL` are exported from core for this, because anything replaying a prefix has to know the period — duplicating the numbers in the web app is how they drift.

**The rule deliberately stops short of eviction pressure**, and it is worth saying why. `zipf-0.75-1m` holds a 10,000-entry cache, so 20,000 events barely fill it and three policies land within 0.001 of each other. That prefix is unrepresentative but not dishonest — a stationary trace shown early, not a scan-heavy trace with no scan. Widening the spread to a useful 0.05 needed 200,000 events and a 282 ms replay on every backwards seek, which is a worse runner than a narrow spread is.

**T41's headline measurement was wrong.** That entry reports replaying 20,000 events at **0.85 ms**; re-measured on the path that actually pays for it — a backwards seek, which reuses the already-generated trace — it is **2 ms**, and 9-13 ms for the longer prefix. The decision it justified is unchanged and if anything better supported, since forward stepping still costs nothing extra and a serialisation API across 30 policies in three languages would have bought those milliseconds at the price of a surface that could drift. But the number was stated as measured fact and was off by 2.5x. The one place snapshots might still earn their keep is kv-cache, where replaying the 4,096-step decode trace costs ~270 ms because every step recomputes attention over the kept set — a real problem for T44's step-back, not for this item.

T44 kv-cache runner + visualization — done 2026-08-30. **The attention weights were misaligned with the positions they coloured.** The vector a policy is handed covers the positions held *before* the step; eviction then changes that list. Post-plan: the full scan, and everything it found — done 2026-08-30. Five adversarial review passes over the whole tree (TypeScript registry, Python, C, web app, CLI/scripts/workflows), each verifying its claims by execution — differential fuzzing against paper-faithful references, live Chromium reproduction, cross-language decision replay. Roughly forty findings; all fixed in this pass, and every new guard was made to fail before being trusted.

**The headline: the registry's hard invariant was broken in two policies.** 2Q and S3-FIFO carried three different ghost-queue semantics in three languages. The TypeScript reference blanked a promoted ghost's ring slot but kept counting the hole toward capacity; Python deleted it from an OrderedDict; C removed the membership entry but left the stale key in the ring, so a later expiry silently killed a live, re-added ghost. Python diverged from TypeScript **on the canonical benchmark traces** (zipf-1.0-100k: 71,471 hits against 71,493, different victims everywhere); C agreed there only by luck and split from TypeScript within a handful of evictions on churny small caches. Every suite was green throughout, because the shared vectors never reach ghost-promotion-while-full and nothing replayed decisions across languages.

**The fix pins the paper's semantics** — a ghost queue holds live keys only; promotion is a removal. Python was already canonical. TypeScript and C both now implement the ghost as a FIFO list over slots with a key-to-slot map (C on `pb_ilist`; TS with the same prev/next arrays Am uses). The first TS attempt used an insertion-ordered `Set`, and the bench damping caught it: V8's tombstone iteration turns steady expire-and-add into O(size), and 2Q's throughput fell 4.07M to 1.27M ops/s before the honest structure went in. Final numbers: 2Q's zipf-1.0-100k hit rate is 0.71471 (the number the Python port produced all along), and the `forgetGhost` linear scan — 299.6M ring probes per canonical run in S3-FIFO, quietly legitimised by the recorded perf baselines — is gone: S3-FIFO 1.82M to 10.7M ops/s on zipf-0.75-1m, 2Q 4.07M to 10.8M, and the `policy.json` O(1) claims are true for the first time. C memory rose honestly (2Q 69.2 to 75.2 bytes/entry, S3-FIFO 82.7 to 93.5 — a list costs links) and the READMEs say so.

**The guard that makes this class impossible to reintroduce silently: committed decision parity.** `scripts/gen-decision-parity.ts` drives all ten cache policies over the four canonical traces plus two deliberately churny LCG streams — the regime where the canonical traces stay silent — and commits an FNV-1a64 hash of every decision stream. Vitest, pytest, and a C test recompute the hashes with their own ports; CI checks the artifact regenerates as a no-op. Proven the required way: fault-injected TS and Python each went red; unfixed C failed naturally. The two new hand-authored vector cases (ghost promotion while the queue is full) carry behavioural tails because of a discovery worth recording: **the C vector runner silently skips `queueOf` probes** — a membership assertion polices two languages, an eviction order polices three.

**The web app's seams (13 findings, all reproduced live before fixing).** The tutorial's centrepiece comparison was dead in production — the worker prefixed `tutorial/evict-newest` with the domain — and shipped invisibly because smoke.mjs never visited /tutorial/, the one page with two runners; those two also fought over the URL fragment and the keyboard.
